## Summary
CAPCOM analyzed SDK/MCP architectural boundary: adapters duplicate inferior functionality that MCP servers already provide.

## Key Findings
- MCP Config exists (`SquadSessionConfig.mcpServers`) but Squad never introspects it
- Copilot SDK handles MCP transport; Squad has zero visibility into available tools
- Two parallel tool systems: Squad tools (via `ToolRegistry`) + MCP tools (via SDK)
- Adapters provide synchronous CLI wrappers (`execFileSync`) — blocks, doesn't scale
- Normalization (GitHub issues → WorkItem) is lossy, agents handle variance naturally

## Root Issues
1. Squad has zero MCP client capability — can't discover available tools
2. Adapters were designed for SDK consumers that never materialized
3. MCP servers provide async, remote-capable, ecosystem-friendly transport (adapters don't)
4. Capability discovery missing: agents can't declare tool requirements

## Recommendations
1. **Phase 1 (v0.9.0):** Deprecate adapters with migration guide to MCP
2. **Phase 2 (v1.0.0):** Remove adapter code entirely
3. **Enhance MCP:** Add SDK `getAvailableTools()` API for capability negotiation
4. **Unify Tool Filtering:** Single `requiredTools`/`allowedTools`/`excludedTools` across Squad + MCP

## Decision Confidence
**Unanimous with Flight and EECOM.** Adapters are solved by MCP; Squad's job is orchestration, not platform wrapping.
